# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This folder is a Next.js codebase living inside the larger MazyOS content-ops
workspace (`../CLAUDE.md`, `../_memoria/`, `../identidade/design-guide.md`).
There is no separate git repo here — this folder is part of the MazyOS repo
one level up, so run git commands from `../`.

## Commands

Run from this directory (`MazyOS/site/`):

```bash
npm install       # also runs `prisma generate` via postinstall
npm run dev       # Turbopack dev server, http://localhost:3000
npm run build     # production build
npm run start     # serve the production build
npm run lint      # ESLint (flat config: eslint.config.mjs)
npm run db:migrate   # prisma migrate dev (interactive — see Prisma gotcha below)
npm run db:seed      # categories + 5 products (+ admin user if SEED_ADMIN_* set)
npm run db:studio    # Prisma Studio, browse/edit data directly
```

No test suite is configured.

## Version warnings — read before writing code

This project sits on **three** bleeding-edge majors at once. Don't assume
training-data behavior for any of them; check the actual installed API first.

**Next.js 16** (Turbopack, React 19): global `PageProps<'/route'>` /
`LayoutProps<'/route'>` typed helpers instead of manually typing
`params`/`searchParams`. `middleware.ts` is **deprecated and renamed to
`proxy.ts`** (exported function named `proxy`, not `middleware`) — this repo
already uses the new name (`proxy.ts` at the root). Check
`node_modules/next/dist/docs/` for anything uncertain. See `AGENTS.md`
(regenerated by `next dev`/`next build` — don't hand-edit it).

**Prisma 7**: the schema's `datasource db { }` block has **no `url`**.
Connection URLs live in `prisma7.config.ts` (`datasource.url`, used by the
CLI for migrations — set to `DIRECT_URL`) and are passed explicitly to the
client via a **driver adapter**: `new PrismaClient({ adapter: new
PrismaPg({ connectionString: process.env.DATABASE_URL }) })` (see
`lib/prisma.ts`). The generated client is TypeScript source written to
`lib/generated/prisma/` (gitignored, regenerate with `prisma generate`),
not the old `.prisma/client` output. `prisma migrate dev` refuses to run
non-interactively when a migration has a data-loss warning (e.g. adding a
`@unique`) — write the migration SQL by hand into
`prisma/migrations/<timestamp>_<name>/migration.sql` and apply with `prisma
migrate deploy` instead in that case.

**Auth.js v5** (`next-auth@beta`): `signIn(...)` throws `AuthError` on bad
credentials even with `redirect: false` (that option only changes the
*success* path). See `lib/auth-actions.ts`.

## Critical gotcha: the server/client module boundary

`lib/prisma.ts`, `lib/products.ts`, and `lib/orders.ts` all start with
`import "server-only"` **on purpose**. Prisma's driver adapter pulls in the
`pg` package, which needs Node-only builtins (`net`, `tls`) that don't exist
in the browser. If *any* Client Component imports *any* value — even one
unrelated function like `formatPrice` — from a module that also imports
`prisma`, the whole module (including the `pg` chain) gets bundled for the
browser and the build fails with `Module not found: Can't resolve 'net'`.

That's why formatting/display helpers live in their own Prisma-free files:
- `lib/format.ts` — `formatPrice`, `formatInstallments`
- `lib/order-status.ts` — `ORDER_STATUS_LABELS`

When adding a new helper that a Client Component needs, ask whether it
touches Prisma. If not, it belongs in one of these pure files (or a new one
like them), never added to `lib/products.ts`/`lib/orders.ts`/`lib/admin.ts`.
`import "server-only"` at the top of a file is your build-time tripwire for
this — keep it there.

## Architecture

**Scope:** full e-commerce — accounts, cart, checkout, Mercado Pago payment,
orders, tracking, admin panel. Evolved same-day (2026-08-27) from an
institutional/WhatsApp-only site; see `README.md` for the full rationale,
what's implemented vs. still missing for production, and required env vars.

**Data layer:** PostgreSQL (Supabase) via Prisma 7. 13 models in
`prisma/schema.prisma`: `User`/`Account`/`Session`/`VerificationToken`
(Auth.js), `Address`, `Product`/`Category`, `Cart`/`CartItem`,
`Order`/`OrderItem`/`Payment`/`OrderEvent`. `Payment.providerPaymentId` is
`@unique` (required for the webhook's `upsert`).

**Route groups:** `app/(store)/{carrinho,checkout,checkout/sucesso,checkout/erro}`,
`app/(account)/minha-conta/{pedidos,dados,enderecos,seguranca}`,
`app/admin/{produtos,pedidos,clientes,cupons}`. Route groups don't affect
the URL — `/carrinho` resolves regardless of the `(store)` folder.

**Auth & access control:** Credentials provider (bcrypt), JWT sessions.
`proxy.ts` guards `/minha-conta/*` (any authenticated user) and `/admin/*`
(`role === "ADMIN"`) at the routing layer — but per Next's own guidance,
Proxy doesn't reliably cover Server Actions, so every mutating action in
`lib/account.ts`/`lib/admin.ts` re-checks (`requireUserId()`/
`requireAdmin()`) independently. Don't rely on Proxy alone when adding new
Server Actions.

**Cart:** anonymous carts are keyed by an httpOnly `cart_session_id` cookie;
logged-in carts by `userId`. `mergeCartOnLogin()` (`lib/cart.ts`) folds the
anonymous cart into the user's cart on login/register, summing quantities
and respecting stock.

**Coupons (2026-08-28):** `lib/coupons.ts` (`validateCoupon`, `calculateDiscount`,
`getActiveStoreCoupon`, `getActiveScopedCoupons`) is the single source of
truth for whether a coupon still applies — `Coupon.productId`/`.categoryId`
(both nullable, mutually exclusive) make a coupon store-wide, product-scoped,
or category-scoped. Never trust a stored `Cart.couponId` at face value:
`lib/cart.ts`'s `getCart()` re-validates it against current cart
contents/dates/limits on *every* read and silently clears it (with a
`couponError`) the moment it stops qualifying, and `createOrderFromCart`
(`lib/orders.ts`) re-validates independently again at order time before
writing `Order.discountTotal`/`.couponId` and incrementing
`Coupon.usedCount`, inside the same `$transaction` as stock decrement.
`ProductCard`/product-detail pages show an `OfferBadge` via
`lib/products.ts`'s `attachOffers()` (matches `getActiveScopedCoupons()`
against each product/category); `AnnouncementBar` (in `app/layout.tsx`)
shows a live countdown for the soonest-expiring active store-wide coupon.
`components/CountdownBar.tsx`'s `formatRemaining()` only shows
minute-precision once more than a day remains (no seconds) — expected, not
a bug, if a countdown value looks like it "isn't ticking" during a quick check.

**Orders & stock:** `createOrderFromCart` (`lib/orders.ts`) runs inside a
`$transaction` and decrements stock with `updateMany({ where: { stock: {
gte: quantity } } })` per line — if any line's condition fails (race between
two checkouts on the last unit), the whole transaction rolls back with a
clear error instead of creating a phantom order. Cancel/refund
(`restoreOrderStock`) adds the stock back.

**Payment (embutido no site, 2026-09-19):** checkout usa o **Payment Brick**
(`@mercadopago/sdk-react`) em vez do Checkout Pro — cartão, Pix e boleto são
cobrados direto na página, sem redirecionar pro Mercado Pago (só o botão de
pagar com saldo/conta Mercado Pago faria isso, e por isso foi tirado das
opções — ver `customization.paymentMethods` em `CheckoutPayment.tsx`).
`lib/payment/` é uma interface de gateway explícita (`PaymentGateway` em
`types.ts`) com duas implementações — `mercadopago.ts` (ativa:
`Payment.create()` a partir do `formData` que o Brick devolve no `onSubmit`,
`WebhookSignatureValidator` pra assinatura do webhook — tudo do SDK oficial
`mercadopago`, não HMAC na mão) e `stripe.ts` (stub inerte, `npm install
stripe` primeiro se ativar). `lib/checkout.ts` tem dois Server Actions:
`createOrderAction` (form de identificação/entrega/frete → cria o `Order`
`PENDING_PAYMENT`, não cobra nada) e `payOrderAction` (chamada pelo
`onSubmit` do Brick com o `formData` — cobra e aplica o resultado na hora,
sem esperar webhook). Os dois caminhos (`payOrderAction` síncrono e o
webhook, que sempre chega também, às vezes antes) convergem em
`lib/payment/apply-event.ts`'s `applyPaymentEvent` — upsert idempotente do
`Payment` (`providerPaymentId` é `@unique`), então processar o mesmo evento
duas vezes é seguro. `CheckoutPayment.tsx` trata os três resultados: `PAID`
→ redireciona pra `/checkout/sucesso`; `PENDING` (Pix/boleto) → painel
próprio (QR code/copia-e-cola ou link do boleto) que faz polling de
`getOrderStatusAction` a cada 4s e redireciona sozinho quando o webhook
confirmar — **não** usa o Status Screen Brick da MP, pra manter a
identidade visual da marca; `FAILED` (cartão recusado) → mensagem traduzida
por `status_detail` (`DECLINE_MESSAGES`) e o Brick remonta do zero (`key`
bump) pro cliente tentar outro cartão, sem sair do pedido nem recriar
`Order`. Precisa de `NEXT_PUBLIC_MERCADO_PAGO_PUBLIC_KEY` além de
`MERCADO_PAGO_ACCESS_TOKEN`/`WEBHOOK_SECRET` — sem ela o Payment Brick não
monta. Sem `MERCADO_PAGO_ACCESS_TOKEN`, `payOrderAction` ainda assim cria o
`Order` real (`createOrderAction` não depende do gateway) e só falha, com
mensagem verbatim, na hora de cobrar — nunca finge sucesso.

**Shipping (Melhor Envio, 2026-09-19):** `lib/melhor-envio.ts` (server-only)
is the whole integration; `lib/shipping-rules.ts` holds the Prisma-free bits
(free-shipping threshold R$ 299 — keep `components/home/BenefitsBar.tsx`'s
copy in sync — plus `SHIPPING_BOX` and `shipmentWeightKg`). **Todo pedido sai
numa caixa única** (18,5 × 9,5 × 12 cm, tara 80 g): a cotação usa o modo
`package` da API do Melhor Envio, não `products`, com peso = Σ(peso do produto
× qtd) + tara somada **uma vez só** por envio. Por isso o admin pede só o
**peso** do produto; as colunas `heightCm`/`widthCm`/`lengthCm` continuam no
schema mas sem uso. Se algum produto passar a não caber nessa caixa, isso
precisa virar caixa por produto.
Checkout quotes via the `getShippingOptionsAction` Server Action
(`lib/shipping.ts`, always from the server-side cart), and
`createOrderFromCart` re-quotes independently and rejects a service that's no
longer offered — same never-trust-the-client rule as coupons. Price charged is
the re-quoted one. When the Mercado Pago webhook moves an order to `PAID`,
`sendOrderToMelhorEnvio` inserts it into the Melhor Envio cart (the merchant
pays/prints the label there); a `shippingStatus: "sending"` claim makes it
safe against duplicate MP webhooks, and failures land in
`Order.shippingError` (admin-only — **`OrderEvent` rows are customer-visible**
on the tracking and account pages, so never write internal errors there).
Status/tracking come back via `app/api/webhooks/melhor-envio` (X-ME-Signature)
and a daily Vercel cron (`vercel.json` → `app/api/cron/melhor-envio`, needs
`CRON_SECRET`) that retries failed inserts and re-syncs in case a webhook was
lost. Product measures are edited in `../admin/` (Produtos → Embalagem).

**Styling:** Tailwind CSS v4, no `tailwind.config.*` — tokens live in
`app/globals.css` under `@theme` and mirror `../identidade/design-guide.md`
(light/premium palette, reconciled with that file this session).

**Fonts:** self-hosted via `next/font/local` in `app/layout.tsx`, files in
`app/fonts/` (Fontsource builds of the Google Fonts, latin subset, OFL) —
**not** `next/font/google`, whose build-time fetch failed intermittently on
Vercel and broke production deploys (2026-11-18; `../admin/` got the same fix).
Archivo Black
(`font-display`, a placeholder; the brand's official display face isn't
chosen yet — see the comment above its declaration for a font-swap bug to
re-check if replacing it), Oswald (`font-heading`), Inter (`font-body`).

**Animation:** `animejs` v4 (`createScope`/`onScroll`/`stagger` — this API
differs from the more commonly-known v3). `components/Reveal.tsx` is the
generic scroll-triggered fade/slide wrapper (animates `.reveal-item`
descendants); `components/home/Hero.tsx` does a mount-triggered stagger.

**Path alias:** `@/*` resolves to this directory's root (not `src/`).
